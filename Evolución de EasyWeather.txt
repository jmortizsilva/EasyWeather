Evolución de EasyWeather: observaciones reales, avisos meteorológicos, polen y calidad del aire
Quiero que trabajes sobre el repositorio actual de EasyWeather, sin reescribir la aplicación ni cambiar su arquitectura innecesariamente.
El objetivo es evolucionar la aplicación meteorológica que ya existe para que pueda diferenciar claramente entre:
1. 
Datos meteorológicos observados/medidos realmente, principalmente mediante AEMET.
2. 
Previsiones meteorológicas, que actualmente proceden de Open-Meteo y quiero conservar.
3. 
Avisos meteorológicos oficiales, principalmente de AEMET.
4. 
Previsión de polen, idealmente mediante CAMS/Copernicus.
5. 
Calidad del aire, utilizando una fuente apropiada para observaciones reales y CAMS u otra fuente adecuada para previsiones.
6. 
Alertas y notificaciones, ampliando el sistema existente sin romperlo.
La prioridad es mantener todo lo que funciona actualmente y añadir estas capacidades de forma incremental, limpia, mantenible y accesible.

NO quiero sustituir Open-Meteo.
Quiero una arquitectura híbrida.
La responsabilidad de cada fuente debe quedar claramente separada:
Open-Meteo
Mantenerlo como fuente principal para:

previsión diaria;
•

•

•

• 
amanecer/atardecer;
• 
y las demás variables que EasyWeather ya utiliza.
No elimines ni rompas la integración existente de Open-Meteo.
AEMET
Añadirlo como fuente principal para España para:
• 
observaciones meteorológicas reales de estaciones;
• 
temperatura observada;
• 
humedad observada;
• 
viento observado;
•

•

Investigar e integrar, cuando sea técnicamente viable:

predicción de calidad del aire.
Fuente oficial/local de calidad del aire
Investigar qué fuente es más apropiada para obtener observaciones reales de calidad del aire en España.
No asumas que CAMS es la mejor fuente para observaciones locales. Diferencia:
•

•

•

5. Estaciones AEMET
Necesito poder determinar cuál es la estación AEMET más apropiada para una ubicación.
La aplicación ya dispone de:
latitud
longitud
nombre del lugar
zona horaria
Utiliza esas coordenadas.
Quiero un sistema que:
1. 
Obtenga/conserve el inventario de estaciones AEMET.
2. 
Guarde al menos:
• 
identificador de estación;
• 
nombre;
• 
latitud;
• 
longitud;
• 
altitud si está disponible;
• 
provincia;
• 
municipio si está disponible.
3. 
Calcule la distancia entre una ubicación y las estaciones.
4. 
Seleccione la estación apropiada.
5. 
Evite recalcular o descargar innecesariamente el inventario.
6. 
Utilice caché.
Puedes utilizar Haversine u otro método apropiado.
No quiero una dependencia geoespacial pesada si no es necesaria.
 
6. Distancia máxima de una estación
No debemos afirmar que una observación de una estación situada a muchos kilómetros representa exactamente la ubicación del usuario.
Diseña una política razonable.
Por ejemplo:
estación suficientemente cercana
    → mostrar observación AEMET

ninguna estación suficientemente cercana
    → utilizar Open-Meteo como fallback
El valor exacto de distancia máxima debe ser una decisión técnica que debes justificar.
No quiero mostrar una observación de AEMET de una estación muy alejada como si fuera la temperatura exacta del usuario.
 
7. Diferenciar OBSERVACIÓN de PREVISIÓN
Esto es MUY IMPORTANTE.
Actualmente EasyWeather utiliza Open-Meteo para la información current.
Quiero evitar que la interfaz presente una predicción/modelo como si fuese una medición real.
Debemos diferenciar conceptualmente:
OBSERVACIÓN

Temperatura: 31,7 °C
Fuente: AEMET
Estación: Madrid-Retiro
Observado: 20:00
de:
PREVISIÓN

21:00 — 30 °C
Fuente: Open-Meteo
No mezcles ambas cosas.
 
8. Modelo de datos
Revisa src/types.ts y modifica los tipos de forma que quede clara esta diferencia.
No quiero simplemente añadir campos arbitrarios a CurrentConditions.
Prefiero una estructura conceptualmente similar a:
interface CurrentObservation {
  temperature?: number;
  humidity?: number;
  windSpeed?: number;
  windDirection?: number;
  precipitation?: number;

  observedAt: string;

  source: 'aemet';

  station: {
    id: string;
    name: string;
    latitude: number;
    longitude: number;
    distanceKm?: number;
  };
}
Adáptalo a los tipos reales del proyecto.
Si consideras mejor otra estructura, propónla antes de aplicarla.
También quiero conservar la información actual de Open-Meteo que la aplicación necesite.
 
9. Fallback
La aplicación no debe quedarse sin información porque AEMET esté temporalmente inaccesible.
Diseña:
AEMET disponible + estación válida
    → observación AEMET

AEMET no disponible
    → conservar/mostrar datos disponibles de Open-Meteo

AEMET disponible pero estación demasiado lejana
    → utilizar Open-Meteo como estimación/modelo

Open-Meteo tampoco disponible
    → utilizar la estrategia de error/caché que ya tenga EasyWeather
No ocultes silenciosamente los errores.
Internamente deben registrarse adecuadamente.

Añade una integración independiente para avisos.
Quiero utilizar los datos oficiales de AEMET y, cuando sea posible, su información georreferenciada.
La aplicación debe poder determinar si la ubicación seleccionada está afectada por un aviso.

Adapta los campos a lo que realmente entregue AEMET.
 
11. No confundas avisos oficiales con alertas personales
Quiero dos conceptos diferentes.
Aviso oficial
Ejemplo:
Aviso naranja por temperaturas máximas
Fuente: AEMET
Alerta personal
Ejemplo:
Tu alerta de temperatura
La previsión supera los 35 °C
Nunca presentes una regla creada por el usuario como si fuera un aviso oficial.
 
12. Niveles de aviso
Utiliza los niveles oficiales que entregue AEMET.
No calcules por tu cuenta:
40 °C = aviso rojo
si AEMET no ha emitido ese aviso.
AEMET es la autoridad para los avisos oficiales.
La aplicación puede tener sus propias reglas de alerta, pero deben mostrarse como alertas personales.
 
13. Notificaciones de avisos AEMET
Reutiliza el sistema de notificaciones existente.
No crees un segundo sistema de push.
El flujo debe ser:
Cloudflare Worker
    ↓
comprueba avisos AEMET
    ↓
identifica usuarios afectados
    ↓
comprueba preferencias
    ↓
comprueba si el aviso ya fue enviado
    ↓

Necesito evitar duplicados.
Por ejemplo:

    → enviar

siguiente ejecución
    → mismo aviso
    → NO enviar otra vez

AEMET actualiza aviso
    → nuevo estado/id/versión
    → enviar nueva notificación si corresponde
Diseña el mecanismo de deduplicación correctamente.

40. Principio final
La aplicación debe ser honesta sobre la naturaleza de cada dato.
Nunca presentar:
modelo → como observación
ni:
alerta propia → como aviso oficial
ni:
dato antiguo → como dato actual
Cada dato importante debería poder responder claramente a:
¿Qué valor es?
¿De dónde viene?
¿Es observado o previsto?
¿A qué hora corresponde?
¿Para qué ubicación?
Prioriza precisión, robustez, accesibilidad y mantenimiento sobre añadir muchas funcionalidades rápidamente.
